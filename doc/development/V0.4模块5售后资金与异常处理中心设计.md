# V0.4 模块 5：售后资金与异常处理中心设计

日期：2026-08-05
分支：`dev`

## 目标

在现有若依“售后与资金”业务域下增加一个统一运营中心，集中呈现售后审核、退款执行、支付/退款对账差异、异常告警和补偿任务。中心只负责聚合查询、优先级排序和正确的操作入口；业务状态变化继续由现有售后、退款、对账和补偿模块完成。

本模块不新增角色体系，不把客服审核和财务退款合并为一个按钮，不直接修改订单、支付或库存状态。

## 当前能力与缺口

- 订单项售后已有列表、详情、审核通过、驳回、确认收货并退款，权限已拆为 `mall:after-sale:audit` 和 `mall:after-sale:refund`。
- 对账已有支付/退款差异查询、忽略、创建补偿、告警查询和告警确认，但页面独立，返回结构不是统一分页模型。
- 补偿任务已有幂等创建、自动执行、重试和手动执行控制器，但没有若依菜单和岗位授权入口。
- 订单中心可以查看风控记录，但当前没有专门的异常支付工作项视图。

## 页面方案

统一页面路由：`/mall/after-sale-funds/center`，挂在现有“售后与资金”目录下，作为第一个业务入口；原“售后处理”和“对账与告警”页面保留，作为需要完整表格操作时的专用页面。

### 桌面端

```text
售后与资金 / 处理中心
┌────────┬────────┬────────┬────────┬────────┬────────┐
│待审核  │待退款  │退款失败│待处理差异│未确认告警│人工补偿│
└────────┴────────┴────────┴────────┴────────┴────────┘
┌───────────────────────────────────────┬──────────────┐
│ 工作队列：售后审核 | 退款执行 | 对账差异 | 补偿任务 │ 优先处理 │
│ 筛选：业务单号 / 订单号 / 状态 / 时间                 │ 高风险条目 │
│ 列表：编号、订单、金额、状态、风险信号、更新时间、操作 │ 状态说明   │
└───────────────────────────────────────┴──────────────┘
点击条目 -> 右侧详情抽屉：证据、金额计算、支付/退款流水、对账差异、补偿历史、操作记录
```

### 移动端

- 六项统计改为两列卡片，数字和状态颜色保持固定高度。
- 工作队列改为横向分段控件，列表使用单列业务卡片；金额、状态和主操作保持首屏可见。
- 详情使用底部抽屉，审核、退款、确认告警等主操作固定在抽屉底部；不出现页面级横向滚动。
- `prefers-reduced-motion: reduce` 下关闭卡片位移和抽屉过渡。

## 工作队列

| 队列 | 数据来源 | 默认优先级 | 可执行动作 |
| --- | --- | --- | --- |
| 售后审核 | `mall_item_after_sale` | 待审核、质量问题凭证缺失、临近期限 | 客服/运营主管审核通过或驳回 |
| 退款执行 | 售后单与退款单 | 退款失败、退款中超时、退货已寄出 | 财务/运营主管按服务端金额发起或确认退款 |
| 对账差异 | `mall_reconciliation_diff` | 高金额、超时未处理、状态金额双差异 | 财务/运营主管忽略或创建补偿 |
| 异常告警 | `mall_reconciliation_alert`、支付补偿任务 | `CRITICAL`、超时未确认 | 财务/运营主管确认告警 |
| 补偿任务 | `mall_compensation_task` | `MANUAL`、`FAILED`、重试次数高 | 财务重试；运营主管可重试和手动执行 |

异常支付不新建重复表：支付结果差异通过对账差异展示，迟到支付原路退款通过 `LATE_PAYMENT_REFUND` 补偿任务展示；风控记录继续从订单中心只读查看。

## 岗位职责与权限

| 岗位 | 中心入口 | 售后审核 | 退款执行 | 差异/告警 | 补偿任务 |
| --- | --- | --- | --- | --- | --- |
| 运营主管 | 可见 | 通过/驳回 | 发起/确认 | 忽略、创建补偿、确认告警 | 查看、重试、手动执行 |
| 商品运营 | 不可见 | 无 | 无 | 无 | 无 |
| 客服售后 | 可见 | 通过/驳回 | 无 | 无 | 无 |
| 仓储履约 | 不可见 | 无 | 无 | 无 | 无 |
| 财务风控 | 可见 | 只读结果 | 发起/确认 | 忽略、创建补偿、确认告警 | 查看、重试 |

硬边界：客服永远不能调用退款、补偿或告警确认接口；财务永远不能调用售后审核接口；商品运营和仓储履约不获得中心父菜单。所有按钮隐藏只用于体验，服务端 `@PreAuthorize` 和 Service 状态校验才是最终约束。

## 外部接口（模块接口）

新增一个深模块聚合接口，避免页面分别拼接五套数据：

```text
GET /mall/after-sale-funds/center
  query: tab, status, businessNo, orderNo, from, to, pageNum, pageSize
  response:
    summary: pendingReview, refundPending, refundFailed,
             openDiffs, openAlerts, manualCompensations
    rows: [{ kind, recordId, businessNo, orderNo, amount,
             status, priority, riskSignal, updatedAt }]
```

接口只返回当前角色可见的工作项，默认最多 10 条摘要；完整操作仍跳转既有详情/专用页面。接口内部通过既有 Mapper/Service 读取，不把 SQL 写入 Controller。

现有写接口保持不变并作为唯一状态变更入口：

- `/mall/after-sale/item-orders/{id}/approve|reject|refund`
- `/mall/reconciliation/diffs/{id}/ignore|create-compensation`
- `/mall/reconciliation/diffs/alerts/{id}/ack`
- `/mall/compensation/tasks/{id}/retry`、`/run`

## 菜单与迁移方案

新增版本化迁移 `V2.17.0__mall_after_sale_funds_center.sql`，回滚脚本同名 `_rollback.sql`。

- 新增中心菜单 ID 4000，父菜单 3982，路由 `center`，组件 `mall/after-sale-funds/index`，权限 `mall:after-sale-funds:center:list`。
- 新增中心查询功能权限 ID 4001：`mall:after-sale-funds:center:query`。
- 补齐补偿任务菜单和权限：列表、重试、手动执行；只授予运营主管和财务风控，客服不授予。
- 复用已有售后、对账权限字符串，不改已有菜单 ID、路由和权限含义。
- 迁移必须支持升级、重复升级、回滚、再次升级；回滚不能删除 V0.3/V0.4 既有菜单和业务数据。

## 验收顺序

设计确认 -> 菜单/权限迁移 -> 聚合接口单测与权限测试 -> 若依页面构建 -> 五岗位真实链路 -> Edge 1440px/390px -> 升级/重复升级/回滚/再升级 -> 独立提交。

## 不在本模块

- 不重做商城用户端 UI，不修改 `ai-web/` 和原型目录。
- 不新增消费者等级、会员会话或图形验证码；风险触发式验证码保留到后续会员运营与登录安全模块。
- 不接入真实支付/快递第三方接口，不绕过现有 RefundPort、对账和补偿 Adapter。
