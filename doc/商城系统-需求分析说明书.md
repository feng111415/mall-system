# 商城系统需求分析说明书

> 文档版本：V0.1（已确认）  
> 编写日期：2026-07-21  
> 项目定位：基于 RuoYi-Vue 的单商户 B2C 实物商品商城  
> 本文档只定义业务需求，不提前限定具体技术实现。

## 1. 项目概述

### 1.1 建设背景

建设一套面向普通消费者的在线商城。消费者可以浏览商品、选择规格、加入购物车、提交订单、完成模拟支付并查看物流进度；运营人员通过管理后台维护商品、库存、订单、售后和营销内容，形成完整的线上交易闭环。

### 1.2 首期目标

1. 打通“浏览商品 -> 加入购物车 -> 提交订单 -> 支付 -> 发货 -> 收货”的主流程。
2. 打通“申请售后 -> 审核 -> 退款/退货 -> 完结”的逆向流程。
3. 提供商品、库存、订单、会员和运营数据的统一后台。
4. 使用角色和权限控制后台操作，保留关键业务操作记录。
5. 先完成可演示、可扩展的单商户版本，不在首期引入多商户结算复杂度。

### 1.3 成功标准

- 用户可以独立完成一次从选购到确认收货的完整交易。
- 库存不会因重复提交或重复回调被多次扣减。
- 后台可以追踪一笔订单的商品、金额、支付、发货和售后记录。
- 商品下架后不可新购，但历史订单仍能正常查看商品快照。
- 不同后台角色只能看到并执行已授权的菜单和操作。

## 2. 项目范围

### 2.1 首期范围（P0）

- 用户端：注册登录、首页、分类、搜索、商品详情、购物车、结算、地址、订单、模拟支付、物流信息、售后、个人中心。
- 运营后台：工作台、分类、品牌、商品、SKU、库存、订单、发货、售后、会员、风险订单、轮播内容、系统权限和操作日志。
- 公共能力：短信验证码、隐私授权记录、操作审计、版本发布与回滚、图片上传、统一异常处理、数据字典、消息提示、Excel 导出。

### 2.2 增强范围（P1，首期完成后）

- 优惠券、满减活动、收藏、商品评价、站内消息。
- 真实微信支付或支付宝支付。
- 对接快递公司的实时物流轨迹。
- 销售趋势、商品排行、用户复购等经营分析。

### 2.3 暂不纳入

- 多商户入驻、店铺结算和平台抽佣。
- 拼团、秒杀、直播、分销、会员等级和积分体系。
- 虚拟商品、预售、跨境、门店自提。
- 复杂仓库调拨、采购和供应商管理。
- 原有钢琴作业、票务、课程和知识库练习模块，不属于商城产品范围。

## 3. 用户与角色

| 角色 | 使用端 | 核心职责 |
| --- | --- | --- |
| 游客 | 用户端 | 浏览首页、分类、搜索和商品详情；下单前必须登录 |
| 商城会员 | 用户端 | 管理地址和购物车，创建并支付订单，确认收货，申请售后 |
| 运营人员 | 管理后台 | 维护分类、品牌、商品、轮播内容和上下架状态 |
| 仓库人员 | 管理后台 | 查看待发货订单，填写物流公司和运单号，执行发货 |
| 客服人员 | 管理后台 | 查询订单，审核并处理售后申请 |
| 系统管理员 | 管理后台 | 管理用户、角色、菜单、参数、字典和日志，并拥有商城全量权限 |

说明：首期可以由一个管理员账号同时承担运营、仓库和客服职责，但权限模型必须允许后续拆分。

## 5. 详细功能需求

### 5.1 账号与会员

- `FR-USER-001` 用户端以“手机号 + 短信验证码”作为主要注册登录方式，并保留“手机号 + 密码”登录作为备选方式。
- `FR-USER-002` 未登录用户可浏览商品；购物车持久化、结算、订单和售后要求登录。
- `FR-USER-003` 被停用的会员不可登录和创建新订单，但历史数据不得删除。
- `FR-USER-004` 个人中心展示昵称、头像、手机号和各状态订单数量。
- `FR-USER-005` 手机号等敏感信息在后台列表中默认脱敏展示。
- `FR-USER-006` 手机号标准化后必须全局唯一，不得直接作为对外展示的会员编号或数据库主键。
- `FR-USER-007` 未注册手机号使用验证码登录时，界面必须明确提示“验证成功后将创建商城账号”；用户主动勾选用户协议和隐私政策后才能创建账号，勾选框不得默认选中。
- `FR-USER-008` 系统应记录用户同意的协议类型、协议版本、同意时间和必要的审计信息；协议更新涉及处理目的重大变化时，应重新取得同意。
- `FR-USER-009` 用户可在个人中心更正手机号和个人资料、撤回非必要授权并申请注销账号；注销前需校验未完结订单、售后和余额等业务约束。
- `FR-USER-010` 注销后停止账号使用，并按照法律要求和履约、售后、财务审计所需期限处理历史交易数据；不得简单物理删除交易凭证。

### 5.1.1 短信验证码

- `FR-SMS-001` 注册、验证码登录和更换手机号使用不同短信业务场景及模板，验证码不得跨场景使用。
- `FR-SMS-002` 验证码默认使用 6 位数字、5 分钟有效、校验成功后立即失效；同一验证码最多允许错误输入 5 次，阈值可配置。
- `FR-SMS-003` 同一手机号 60 秒内不可重复发送，默认每天最多发送 5 次；同时按 IP 和设备限制发送频率，异常请求先通过图形验证码。
- `FR-SMS-004` 发送接口无论手机号是否已经注册，都返回不暴露账号存在性的统一提示，防止批量探测会员手机号。
- `FR-SMS-005` 验证码只能保存摘要及有效期，不得明文落库、写入日志或返回给用户端；开发环境的模拟验证码必须与生产配置隔离。
- `FR-SMS-006` 同一验证码的发送和核验操作必须具备幂等与并发保护，不能因重复点击发送多条短信或重复完成注册。
- `FR-SMS-007` 生产环境只使用已审核的短信签名和模板，通过独立短信服务适配层接入供应商，并记录请求编号、发送结果和失败原因，不记录验证码正文。
- `FR-SMS-008` 身份验证短信只用于完成用户主动发起的身份验证；营销短信必须取得独立授权，并提供便捷退订方式，不得复用验证码授权。
- `FR-SMS-009` 短信发送失败时允许重新获取或使用密码登录，界面不得把供应商内部错误、手机号完整信息或验证码暴露给用户。

### 5.2 商品中心

- `FR-GOODS-001` 商品以 SPU 表示一个商品，以 SKU 表示可实际购买的规格组合。
- `FR-GOODS-002` 商品必须归属一个有效分类，可选品牌，并至少有一个可售 SKU 才能上架。
- `FR-GOODS-003` 商品详情展示主图、轮播图、详情、SKU 价格区间、销量和库存状态。
- `FR-GOODS-004` 下架或删除商品不可新加入购物车和下单，购物车中应标为失效。
- `FR-GOODS-005` 后台支持按名称、分类、品牌和上下架状态查询商品。
- `FR-GOODS-006` 修改商品信息不得改变历史订单中的商品名称、规格、单价和图片快照。

### 5.3 购物车

- `FR-CART-001` 同一用户、同一 SKU 在购物车中只保留一条记录，重复加入时累加数量。
- `FR-CART-002` 购物车数量必须大于 0，且不得超过当前可用库存和单次购买上限。
- `FR-CART-003` 合计金额只计算已勾选且仍有效的商品。
- `FR-CART-004` 进入结算和提交订单时必须重新校验价格、状态和库存，不能只信任前端数据。
- `FR-CART-005` SKU 可用库存为 0 时，“加入购物车”和“立即购买”按钮不可用，并明确展示“已售罄”；服务端同时拒绝加购请求。
- `FR-CART-006` 加入购物车不锁定库存。只有订单创建成功后才锁定库存，不能以购物车数量作为库存占用依据。
- `FR-CART-007` 已在购物车中的 SKU 后续售罄时，保留购物车项并标记“已售罄”，自动取消勾选且不计入合计金额；用户可以删除或等待补货。
- `FR-CART-008` 当前可用库存低于购物车数量时，提示“仅剩 N 件”并阻止结算，要求用户调整数量；系统不得在用户不知情时静默修改购买数量。
- `FR-CART-009` 商品页展示有库存但加购时库存已变化的，以服务端实时校验为准，返回明确的库存不足提示并刷新商品库存状态。

### 5.4 订单与结算

- `FR-ORDER-001` 用户从购物车已勾选商品或商品详情的“立即购买”进入结算页。
- `FR-ORDER-002` 提交订单时保存收货人、电话、地址、商品、规格、单价和优惠的快照。
- `FR-ORDER-003` 订单金额由商品总额、运费、优惠金额计算，首期公式为：应付金额 = 商品总额 + 运费 - 优惠金额。
- `FR-ORDER-004` 订单创建成功后锁定库存，生成全局唯一且不可修改的订单号。
- `FR-ORDER-005` 未支付订单可由用户主动取消，也可在 30 分钟后自动关闭；关闭后释放锁定库存。
- `FR-ORDER-006` 待发货订单可由后台取消，已发货订单不可直接取消，应走售后流程。
- `FR-ORDER-007` 用户确认收货后订单完成；发货 15 天后可由定时任务自动确认收货。
- `FR-ORDER-008` 所有订单状态变化需记录操作人、操作时间、原状态、目标状态和备注。
- `FR-ORDER-009` 用户进入结算页时获取一次性提交令牌；首次提交成功后令牌失效，同一令牌重复提交必须返回首次创建的订单，不得创建新订单。
- `FR-ORDER-010` 点击“提交订单”后，用户端立即禁用按钮并显示处理中；请求失败后才允许重新操作。
- `FR-ORDER-011` 服务端必须使用会员 ID 与业务幂等键建立唯一约束，不能只依赖前端防抖或 Redis 临时锁。

### 5.5 支付

- `FR-PAY-001` 首期使用模拟支付，保留支付单号、支付方式、支付金额和支付时间。
- `FR-PAY-002` 支付成功必须校验订单存在、状态为待付款且支付金额与订单金额一致。
- `FR-PAY-003` 同一支付结果被重复提交时只能成功处理一次。
- `FR-PAY-004` 支付成功后订单转为待发货，锁定库存转为实际销售扣减。
- `FR-PAY-005` P1 接入真实支付时，支付回调必须验签并以服务端查询结果为准。

### 5.6 库存

- `FR-STOCK-001` 每个 SKU 维护可用库存和锁定库存，库存不得为负数。
- `FR-STOCK-002` 创建订单锁定库存；取消或超时释放；支付成功确认扣减。
- `FR-STOCK-003` 后台人工调整库存必须填写原因并产生库存流水。
- `FR-STOCK-004` SKU 可设置低库存阈值，达到阈值后在工作台预警。
- `FR-STOCK-005` 并发提交时，同一份库存不能被多个订单重复占用。

### 5.7 发货与物流

- `FR-SHIP-001` 只有待发货订单可以发货，发货时必须填写物流公司和运单号。
- `FR-SHIP-002` 发货成功后订单转为待收货，并记录发货人和发货时间。
- `FR-SHIP-003` 首期由后台手工维护物流节点；P1 可切换为第三方物流查询。
- `FR-SHIP-004` 用户可在订单详情查看物流公司、运单号和物流节点时间线。

### 5.8 售后与退款

- `FR-AFTER-001` 用户可针对已支付订单中的单个订单项申请仅退款或退货退款。
- `FR-AFTER-002` 申请需填写原因、金额、说明，可上传图片凭证。
- `FR-AFTER-003` 客服可同意或拒绝申请；拒绝必须填写原因。
- `FR-AFTER-004` 退货退款在客服确认收到退货后执行模拟退款。
- `FR-AFTER-005` 退款成功需更新退款金额和售后状态，并记录退款流水。
- `FR-AFTER-006` 同一订单项累计退款金额不得超过其实付金额。

### 5.9 后台权限和审计

- `FR-AUTH-001` 后台使用若依的用户、角色、菜单和按钮权限模型。
- `FR-AUTH-002` 商品上下架、库存调整、订单取消、发货、售后审核和退款必须记录操作日志。
- `FR-AUTH-003` 运营、仓库、客服默认只拥有各自职责所需权限。
- `FR-AUTH-004` 数据导出必须受独立权限控制，并记录导出操作。
- `FR-AUTH-005` 登录、创建、修改、删除、上下架、库存调整、订单取消、发货、退款、风险审核、导入导出、配置修改和完整手机号查看均属于必须审计的操作。
- `FR-AUTH-006` 操作日志至少记录日志编号、请求追踪号、操作人及角色、模块、动作、目标类型与编号、变更前后摘要、IP、客户端信息、执行结果、错误原因和时间。
- `FR-AUTH-007` 日志中的密码、验证码、令牌、完整手机号和支付敏感信息必须脱敏或排除，不得为了审计而扩大敏感信息暴露。
- `FR-AUTH-008` 普通业务人员不得修改或删除操作日志；日志保存期限默认不少于 180 天，具体期限可根据实际合规和经营要求配置。
- `FR-AUTH-009` 商品、分类、轮播和普通配置修改时保存业务版本快照，可选择历史版本恢复；恢复操作生成一个新版本和新日志，不覆盖或删除历史记录。
- `FR-AUTH-010` 库存、订单、支付、退款等交易数据禁止通过“日志回放”直接还原，只能通过库存调整、取消、退款等受控反向业务处理，并继续产生审计记录。

### 5.10 防重复与交易风控

- `FR-RISK-001` 系统应分别记录订单业务状态和风险状态；风险状态至少包括待检测、已通过、待人工审核、已拒绝。
- `FR-RISK-002` 创建订单前执行硬性规则校验。默认同一会员最多保留 3 笔有效待付款订单，超过后拒绝继续下单，并提示先处理已有订单。
- `FR-RISK-003` 对同一会员、设备标识或 IP 的下单频率进行限制。默认 1 分钟内超过 10 次提交尝试时触发限流或图形验证码，阈值可在后台配置。
- `FR-RISK-004` 对短时间内大量购买同一 SKU、频繁取消、长期不支付、多个账号共用设备/IP/手机号/收货地址等行为记录风险信号。
- `FR-RISK-005` 命中明确的恶意占库存规则时，在锁定库存前拒绝请求；命中可疑规则时标记为待人工审核，审核通过前禁止发货。
- `FR-RISK-006` 客服或管理员可查看命中规则、风险分值和关联订单，并执行通过、拒绝、加入黑名单或解除限制；人工操作必须留痕。
- `FR-RISK-007` 处于风险拒绝状态的订单自动关闭并释放库存；已付款订单被拒绝时进入退款处理，不得直接丢弃。
- `FR-RISK-008` 销量和销售额只统计已支付且风控通过的订单；关闭、全额退款和确认刷单的订单不得计入有效经营数据。
- `FR-RISK-009` 登录、注册、领券、提交订单和支付回调分别限流，支付回调以支付平台流水号作为幂等依据，不受普通用户接口限流影响。
- `FR-RISK-010` 基础风控规则列入 P0；设备指纹、机器学习评分和第三方反欺诈服务列入后续增强范围。

### 5.11 事务回滚、补偿与对账

- `FR-TX-001` 创建订单时，订单主记录、订单项、库存锁定、库存流水和幂等结果必须在一个本地数据库事务中完成；任一步失败时全部回滚，不得留下无明细订单或孤立库存记录。
- `FR-TX-002` 取消或关闭订单时，订单状态变更、锁定库存释放和库存流水必须在一个事务中完成；失败时保持原状态并允许安全重试。
- `FR-TX-003` 支付回调处理中，支付流水写入、订单状态变更和库存确认扣减必须原子完成；重复回调只能读取或返回首次成功结果。
- `FR-TX-004` 数据库事务不得跨越短信、支付、物流等外部服务调用。外部调用结果通过业务状态、幂等键、重试任务和补偿任务保证最终一致。
- `FR-TX-005` 用户已支付但本地回调处理失败时，系统应保留原始支付流水并自动重试；达到重试上限后进入异常队列并通知管理员，不得要求用户重复支付。
- `FR-TX-006` 订单已关闭后收到迟到的支付成功通知时，系统不得恢复发货，应生成异常记录并自动发起原路退款或转人工处理。
- `FR-TX-007` 退款只有在支付渠道确认成功后才能标记为退款成功；渠道成功但本地更新失败时，由对账任务补写状态，禁止再次退款。
- `FR-TX-008` 定时对账任务应检查订单、支付、退款、库存锁定与库存流水之间的差异，发现不一致时自动修复可安全修复的记录，其余进入人工处理列表。
- `FR-TX-009` 补偿和重试操作必须限制最大次数、采用退避策略并保存最后错误；人工处理必须通过受权限控制的业务操作完成，不得直接修改数据库。
- `FR-TX-010` 系统应为关键链路提供异常告警，至少覆盖订单创建回滚失败、库存释放失败、支付回调积压、退款异常和对账差异。

### 5.12 代码版本与发布回滚

- `FR-REL-000` 商城进入编码实施前，必须先建立 Git 版本库、完成现有代码基线提交、创建基线版本标签，并准备发布与回滚脚本；上述条件未完成时不得开始商城业务编码。
- `FR-REL-001` 项目源代码必须纳入 Git 版本管理，生产发布只能基于已提交且可追溯的代码，不允许直接以开发人员工作目录发布。
- `FR-REL-002` 每次发布创建唯一版本号或 Git 标签，并记录提交编号、构建时间、变更说明、数据库脚本版本和发布人。
- `FR-REL-003` 构建产物必须不可变并与源代码版本一一对应，至少保留最近 5 个可用版本及其配置模板，以支持快速回退。
- `FR-REL-004` 发布前备份关键配置和数据库，并执行自动健康检查；检查失败时停止继续发布并回退到上一稳定应用版本。
- `FR-REL-005` 数据库结构变化使用按版本排序的迁移脚本管理。应用版本至少与前后相邻一个数据库版本兼容，避免应用回退后无法读取新结构。
- `FR-REL-006` 删除字段、修改字段含义等破坏性数据库变更采用“先兼容、再迁移、后清理”的分阶段方式，不与依赖该字段的代码在同一次发布中直接删除。
- `FR-REL-007` 应用代码回退使用上一版本构建产物重新部署；数据库已产生的新交易数据默认不得随代码一起回滚或覆盖。
- `FR-REL-008` 数据库误变更优先使用修复迁移恢复；只有发生严重损坏且业务确认允许数据回退时，才可从备份恢复，并必须评估备份时间点之后的数据损失。
- `FR-REL-009` 发布、回退、数据库迁移和配置变更必须记录执行人、版本、开始结束时间、结果和失败原因。
- `FR-REL-010` 发布回滚流程必须形成可执行脚本或流水线，并定期在非生产环境演练，不能只停留在文字方案。

### 5.13 API 与接口安全

- `FR-SEC-001` API 地址可以被客户端和网络工具观察到，系统不得依赖隐藏路径、接口名称或前端按钮控制安全，所有保护必须在服务端执行。
- `FR-SEC-002` 接口分为公开接口、会员接口、后台接口和第三方回调接口。除明确列入白名单的公开接口外，默认全部要求认证。
- `FR-SEC-003` 公开接口仅开放商品展示、分类、公开配置、验证码发送等必要能力，并按 IP、设备和接口分别限流；公开不等于无限制访问。
- `FR-SEC-004` 会员接口必须验证会员令牌及数据归属。查询订单、地址、售后时以令牌中的会员身份为准，不信任前端传入的会员 ID。
- `FR-SEC-005` 后台接口使用独立的后台身份和 RBAC 权限，会员令牌不得调用后台接口；退款、库存调整、权限修改等高风险操作需二次确认并完整审计。
- `FR-SEC-006` 支付和物流回调必须验证签名、时间戳、随机数和业务幂等键，必要时叠加来源 IP 白名单；不得仅凭回调地址保密或 IP 白名单判断可信。
- `FR-SEC-007` 生产环境强制 HTTPS，数据库、Redis、对象存储管理端口和应用管理端口不得直接暴露公网；公网只开放反向代理所需端口。
- `FR-SEC-008` JWT 或令牌密钥、数据库密码、短信密钥、支付密钥不得写入源码或提交 Git，必须通过环境变量或密钥管理服务注入，并支持定期轮换。
- `FR-SEC-009` 用户端令牌和后台令牌使用不同受众或命名空间；令牌过期、退出登录、账号停用和密码修改后能够及时失效。
- `FR-SEC-010` CORS 只允许正式用户端和后台域名，不允许生产环境使用 `*` 通配来源、请求头和方法。
- `FR-SEC-011` Swagger/OpenAPI、Druid、健康详情、调试接口和错误堆栈在生产公网关闭；确需使用时仅允许内网或受认证的运维访问。
- `FR-SEC-012` 所有输入使用 DTO 白名单、类型、长度、范围和格式校验；数据库访问使用参数化查询，输出内容按上下文编码，防止越权、SQL 注入、XSS 和批量字段赋值。
- `FR-SEC-013` 文件上传校验扩展名、MIME、文件头、大小和数量，随机化存储名称，上传目录禁止执行；私有售后凭证通过鉴权接口访问，不使用永久公开链接。
- `FR-SEC-014` 统一错误响应不得向客户端返回堆栈、SQL、服务器路径、密钥或第三方内部错误；完整错误仅进入受权限控制的服务端日志。
- `FR-SEC-015` 登录、短信、搜索、商品详情、加购、下单、支付和导出分别设置限流策略；达到阈值时执行延迟、验证码、临时封禁或人工审核。
- `FR-SEC-016` 关键接口执行对象级授权测试，至少覆盖未登录、令牌过期、普通会员访问他人订单、会员访问后台、低权限员工执行退款等场景。
- `FR-SEC-017` 依赖组件定期执行漏洞扫描并及时升级；上线前完成敏感信息扫描、接口权限检查和基础安全测试。
- `FR-SEC-018` 响应设置合理的 HSTS、CSP、`X-Content-Type-Options`、点击劫持防护等安全头，具体策略根据用户端和后台部署方式分别配置。

## 6. 核心业务流程

### 6.1 正向交易流程

1. 用户浏览或搜索商品，选择可售 SKU。
2. 用户立即购买或加入购物车并进入结算。
3. 系统重新校验商品、价格和库存，生成订单并锁定库存。
4. 用户完成模拟支付，订单进入待发货，库存完成实际扣减。
5. 仓库填写物流信息并发货，订单进入待收货。
6. 用户确认收货，订单进入已完成。

### 6.2 订单状态

| 状态 | 含义 | 允许的下一状态 |
| --- | --- | --- |
| 待付款 | 已创建订单并锁定库存 | 待发货、已取消、已关闭 |
| 待发货 | 已支付，等待仓库处理 | 待收货、已取消（后台特殊处理） |
| 待收货 | 已发货，等待签收 | 已完成、售后处理中 |
| 已完成 | 已确认收货，主交易完成 | 售后处理中（售后期限内） |
| 已取消 | 用户或后台取消 | 终态 |
| 已关闭 | 超时未支付自动关闭 | 终态 |

支付状态、订单状态和售后状态必须分别保存，禁止用一个字段混合表达三种状态。

### 6.3 售后流程

1. 用户选择订单项并提交售后申请。
2. 客服审核：拒绝则流程结束；同意仅退款则进入退款；同意退货退款则等待用户寄回。
3. 客服确认收到退货后发起模拟退款。
4. 退款成功，售后单完结，并更新订单已退款金额。

### 6.4 重复点击与风险订单流程

1. 结算页生成一次性提交令牌，用户点击后按钮立即进入处理中状态。
2. 服务端校验令牌、频率、待付款订单数和基础风险规则，再尝试锁定库存。
3. 同一令牌重复到达时直接返回首次订单；不同令牌的高频请求按规则限流或拦截。
4. 普通订单进入正常支付流程；可疑订单记录风险原因，进入待人工审核并禁止发货。
5. 审核通过后恢复正常履约；审核拒绝后关闭订单、释放库存或对已付款订单发起退款。

### 6.5 异常回滚与补偿流程

1. 本地事务执行失败时立即整体回滚，并向用户返回可识别的失败结果；使用同一幂等键重试不会重复创建业务数据。
2. 外部服务调用失败时记录为待重试，不提前把业务标记为成功。
3. 后台任务按照退避策略重试，超过上限后产生告警并进入人工处理列表。
4. 定时对账比较本地订单、支付渠道结果和库存流水，修复可以确定的差异。
5. 无法自动判断的差异由管理员审核处理，所有处理结果写入审计日志。

### 6.6 版本发布与代码回滚流程

1. 从已提交代码构建唯一版本产物，关联 Git 标签、数据库脚本和变更说明。
2. 发布前完成配置与数据库备份，部署后执行健康检查和核心交易冒烟测试。
3. 检查通过后将版本标记为稳定；失败时使用上一稳定产物重新部署。
4. 应用回退后再次执行健康检查，确认其与当前数据库结构兼容。
5. 发布和回退全过程写入发布记录；需要恢复数据库时单独审批并明确可接受的数据损失范围。

## 7. 核心业务规则

1. 所有金额使用十进制金额类型计算和存储，禁止使用浮点数。
2. 前端提交的价格、优惠和应付金额仅作展示，最终金额由服务端计算。
3. 商品和 SKU 使用软删除；订单、支付、库存流水和售后记录不得物理删除。
4. 商品上下架不影响历史订单快照和售后处理。
5. 地址在下单时复制为订单快照，用户后续修改地址不影响已有订单。
6. 订单号、支付单号、售后单号必须全局唯一。
7. 支付、退款、取消、发货等关键操作必须支持幂等，重复请求不能造成重复变更。
8. 库存变化必须有对应业务来源和流水，可追溯到订单或人工调整记录。
9. 前端防抖只改善操作体验，服务端幂等键和数据库唯一约束才是防止重复订单的最终保障。
10. 风险状态不能覆盖订单状态；风控通过、拒绝和人工审核都要保留原始命中规则及处理记录。
11. 风控阈值必须可配置，并允许管理员人工解除限制，避免正常用户因网络重试或家庭共享网络被永久误伤。

## 8. 数据对象

| 领域对象 | 说明 | 关键关系 |
| --- | --- | --- |
| 会员 | 在用户端完成交易的自然人账号 | 拥有地址、购物车和订单 |
| 商品分类 | 用于组织和筛选商品的树形目录 | 包含多个商品 |
| 品牌 | 商品的品牌信息 | 关联多个商品 |
| SPU | 用户认知中的商品主体 | 包含多个 SKU |
| SKU | 带具体规格、价格和库存的可售单元 | 被购物车项和订单项引用 |
| 购物车项 | 会员准备购买的 SKU 和数量 | 归属于会员 |
| 订单 | 一次结算形成的交易单据 | 包含订单项、支付单和物流单 |
| 订单项 | 下单时商品 SKU 的交易快照 | 可分别申请售后 |
| 支付单 | 一次支付尝试及结果 | 关联订单 |
| 库存流水 | SKU 库存变化的审计记录 | 关联订单或人工调整 |
| 物流单 | 发货承运信息和物流节点 | 关联订单 |
| 售后单 | 针对订单项发起的退款或退货退款流程 | 关联订单项和退款记录 |
| 幂等请求记录 | 一次关键业务提交及首次处理结果 | 关联会员、业务幂等键和订单 |
| 风险记录 | 下单过程中命中的规则、风险分值和处理结果 | 关联会员、设备、IP 和订单 |
| 风险名单 | 需要拦截或重点审核的账号、设备、手机号或地址 | 被交易风控规则引用 |
| 验证码记录 | 一次短信验证码发送、有效期和核验结果 | 关联手机号摘要和短信请求编号 |
| 授权同意记录 | 用户对协议或特定个人信息处理活动的同意凭证 | 关联会员和协议版本 |
| 补偿任务 | 外部调用或跨事务流程失败后的重试与修复任务 | 关联订单、支付、退款或物流业务 |
| 对账差异 | 本地业务记录与外部结果或库存流水之间的不一致记录 | 关联补偿任务和人工处理记录 |
| 操作审计日志 | 后台和关键系统操作的不可篡改追踪记录 | 关联操作人、业务目标和请求追踪号 |
| 业务版本快照 | 商品、分类、轮播和普通配置每次修改后的历史版本 | 支持生成新的恢复版本 |
| 发布记录 | 一次应用部署或回退的版本、执行人和结果 | 关联代码标签、构建产物和数据库脚本 |

## 9. 非功能需求

### 9.1 安全性

- 用户端和后台端身份体系隔离，接口按端和权限校验。
- 密码必须加密存储；登录、支付和退款接口需限制重复请求。
- 注册、登录、下单等高频接口需按账号、设备和 IP 分层限流，阈值可配置。
- 所有查询、修改接口必须校验数据归属，会员只能访问自己的订单和地址。
- 上传文件限制类型和大小，禁止执行上传内容。
- 日志中不得记录密码、完整令牌和完整支付敏感信息。

### 9.2 手机号和个人信息合规

- 收集手机号前明确说明处理目的、使用方式、保存范围和联系方式，并提供可访问的用户协议与隐私政策。
- 遵循最小必要原则。注册登录仅要求手机号和验证码，不得强制收集身份证号、通讯录、精确位置等无关信息。
- 手机号在传输过程中使用 HTTPS，在存储、备份、日志、导出和后台页面中采取加密、脱敏或访问控制措施。
- 后台查看完整手机号需具备独立权限，默认脱敏；查看或导出完整信息必须记录操作人、时间和用途。
- 向短信供应商只提供完成发送所必需的手机号、模板和参数，并在隐私政策中说明第三方处理情况。
- 验证短信与营销短信分开管理；未获得营销授权时，不得因用户注册商城而发送广告短信。
- 提供个人信息查询、更正、注销和投诉入口，并制定验证码记录、登录日志和会员资料的保存及删除策略。
- 上线前应结合实际经营地区、短信供应商和业务模式进行合规复核；本文档是产品需求，不替代正式法律意见。

### 9.3 性能与一致性

- 普通列表和详情接口在本地演示环境下目标响应时间小于 500ms。
- 列表必须分页；商品图片使用压缩图或缩略图。
- 创建订单、库存锁定、支付状态变更必须使用事务保证一致性。
- 支付和库存关键接口需使用数据库约束、条件更新或锁机制处理并发。
- 关键外部调用需具备可重试、可补偿、可对账能力，系统重启后未完成任务不得丢失。

### 9.4 可用性与兼容性

- 用户端适配常见手机宽度，后台适配 1366px 及以上桌面浏览器。
- 空列表、加载中、网络失败、商品失效、库存不足均需有明确界面状态。
- 表单需提供必填、格式、长度和业务范围校验，不得只依赖后端报错。

### 9.5 可维护性

- 商城业务与若依基础模块保持边界，使用独立包、菜单和数据表前缀。
- 状态值由统一枚举或字典管理，前后端不得散落魔法数字。
- 核心交易流程需具备自动化测试，至少覆盖正常、重复请求和库存不足场景。
- 源代码、数据库迁移脚本和发布配置必须共同版本化，发布产物需能追溯到唯一代码提交。

## 11. 首期验收标准

1. 新用户可通过手机号和短信验证码注册登录，未勾选协议时不得自动创建账号。
2. 验证码达到发送或错误次数上限后被正确限制，验证码成功使用一次后不可再次使用。
3. 日志和普通后台列表不出现完整手机号、明文验证码、密码或令牌。
4. 用户可维护默认地址、查看授权记录并在满足业务约束时申请注销账号。
5. 管理员可创建包含至少两个 SKU 的商品并完成上下架。
6. 用户可将不同 SKU 加入购物车，修改数量并提交订单。
7. 库存不足时订单创建失败且不会出现负库存。
8. 用户可完成模拟支付，后台可发货，用户可查看物流并确认收货。
9. 未支付订单取消或超时后，锁定库存被正确释放。
10. 用户可针对订单项发起售后，客服可审核并完成模拟退款。
11. 连续点击十次“提交订单”只产生一笔订单，所有重复请求返回同一个订单结果。
12. 重复支付或退款请求不会重复扣库存、重复变更金额。
13. 超过待付款订单上限或下单频率阈值时请求被拦截，且不会额外锁定库存。
14. 可疑订单在后台展示命中规则，审核前不可发货；拒绝后能够正确关闭或退款。
15. 风险订单、关闭订单和全额退款订单不进入有效销量和销售额。
16. 商品修改或下架后，历史订单仍展示下单时的商品快照。
17. 运营、仓库、客服使用不同角色登录时，菜单与按钮权限符合职责。
18. 售罄 SKU 无法新增到购物车；已在购物车中的售罄 SKU 保留并标记失效，不参与勾选、合计和结算。
19. 模拟订单创建过程中任意一步失败时，订单、订单项、库存锁定和库存流水全部回滚。
20. 模拟支付成功但本地处理失败后，重试或对账能够恢复正确状态，且不会要求用户再次支付或重复扣减库存。
21. 订单关闭后收到迟到支付通知时不会进入发货，而是产生异常记录并进入退款流程。
22. 商品被错误修改后，可从历史版本恢复；恢复生成新的版本和操作日志，原历史记录仍保留。
23. 库存、订单和退款不能通过普通日志直接还原，只能执行受权限控制的反向业务操作。
24. 在测试环境发布新版本并模拟健康检查失败后，系统能够使用上一稳定产物完成代码回退，现有交易数据不被覆盖。
25. 任一发布版本都能追溯到代码提交、构建产物、数据库脚本、发布人和操作时间。
26. 未登录访问会员或后台接口返回未认证结果，会员令牌无法访问后台接口。
27. 会员修改 URL 中的订单编号后仍无法查看或操作其他会员的订单、地址和售后数据。
28. 伪造或重复的支付回调因验签或幂等校验失败，不会改变订单、支付和库存状态。
29. 生产环境从公网无法访问 Swagger、OpenAPI、Druid、调试接口和详细健康信息。
30. 生产配置不存在示例密钥、默认口令、通配 CORS 或提交到 Git 的短信、支付和数据库密钥。
31. 售后凭证等私有文件没有永久公开地址，未授权用户无法访问。

## 14. 当前框架安全基线与上线阻断项

当前 RuoYi-Vue 已提供 JWT 认证、Redis 会话、BCrypt 密码散列、图形验证码、接口权限注解和操作日志基础能力，但现有开发配置不能直接用于公网生产环境。

| 当前问题 | 风险 | 上线要求 |
| --- | --- | --- |
| Swagger、OpenAPI 和 Druid 路径被匿名放行 | 接口结构、SQL 和运行信息容易被探测 | 生产关闭或仅允许受认证的内网运维访问 |
| SpringDoc 开发配置启用 | API 文档可直接访问 | 使用环境配置在生产禁用 |
| CORS 允许任意来源、请求头和方法 | 任意网站可从浏览器发起跨域请求 | 改为用户端和后台域名白名单 |
| JWT 使用示例密钥 | 令牌存在被伪造风险 | 使用高强度随机密钥并从安全配置注入 |
| Druid 允许来源为空且使用默认弱口令 | 数据源监控可能被未授权访问 | 生产关闭公网入口并更换独立强口令 |
| 练习模块存在匿名接口 | 与商城无关的旧接口扩大攻击面 | 生产构建移除、隔离或逐项重新授权 |
| `/profile/**` 静态资源整体匿名访问 | 私有上传内容可能被枚举访问 | 区分公开商品图片与私有售后凭证 |
| 数据源允许多语句执行 | SQL 注入一旦发生时影响范围更大 | 无明确业务需要时关闭多语句执行 |

上述任一阻断项未整改并通过验证时，不允许发布商城生产环境。

本需求 V0.1 已于 2026-07-22 确认，并作为架构设计和 HTML 静态模型的输入；后续需求调整以新版本记录，不直接覆盖本次确认结论。
